## Constitution Compliance

- **Authentication & Authorization**: MCP token auth is a deliberate, precedented second channel (mirrors the Telegram `webhookSecret`); every tool call is scoped by the resolved `userId`, never by tool input (tasks 5.3, 5.7, 5.9, 5.11, 5.13). Compliant.
- **Schema-Driven Development**: `UserSettings.mcpUrl` and `regenerateMcpToken` start from a `schema.graphql` update with codegen (tasks 6.1–6.2, 7.1–7.2); the MCP JSON-RPC transport itself is out of scope for this rule per the design. Compliant.
- **Backend Layer Structure / Port Interfaces**: `mcp-handler.ts` and the MCP tools call services/repositories through existing ports, never touch DynamoDB directly (tasks 5.3, 5.7, 5.9, 5.11, 5.13). Compliant.
- **Backend Domain Entities**: `mcpToken` is validated in `User`'s private constructor; `regenerateMcpToken()` returns a new instance rather than mutating (tasks 1.1–1.2). Compliant.
- **Result Pattern**: MCP tool handlers translate the services' existing `Success`/`Failure` results rather than introducing a new error convention (tasks 5.7, 5.9, 5.11, 5.13). Compliant.
- **Data Migrations**: The `mcpToken` backfill is a versioned, idempotent file under `backend/src/migrations/` (task 4.1). Compliant.
- **Vendor Independence / Repository Pattern**: `findOneByMcpToken` goes through the `UserRepository` port; the `McpTokenIndex` GSI is a plain equality lookup (tasks 2.2–2.3, 3.1). Compliant.
- **Finder Method Naming**: `findOneByMcpToken` returns the user or `null` (task 2.2). Compliant.
- **Test Strategy / Co-location**: New tests are co-located next to their source files (`*.test.ts` alongside `*.ts`) across all backend tasks. Compliant.
- **TypeScript Code Generation**: New code follows existing naming/argument conventions (keyword args for 3+ parameters, no abbreviated names) throughout. Compliant.
